OFFICE PURCHASE

项目代码说明书

这个系统把办公用品采购从纸质单变成三条线：员工提交申请，审核人员通过或驳回，通过后生成订单。代码按这个过程分层，不要一上来从第一个文件逐行读。

一条申请怎么走

1. 登录　Login.vue 调用 POST /user/login。UserController 交给 UserServiceImpl，密码用 BCrypt 比对，JwtUtil 签发令牌。
2. 之后的请求　浏览器在请求头放 Authorization: Bearer 令牌。AuthInterceptor 先解析令牌，再按方法上的 RequireRole 决定能不能进。
3. 提交　员工调用 POST /apply/submit。PurchaseApplyServiceImpl 写入申请主表和明细，状态是“待审批”。
4. 审批　审核人员调用 POST /apply/audit。驳回必须写意见。通过时，同一事务里插入一条“待采购”订单。
5. 跟单　管理员调用 PUT /order/status，把订单改成采购中、已到货或已完成。这里不扣库存。

分层约定

Controller 只接收参数和返回 Result。业务规则放在 ServiceImpl。Mapper 只负责和表说话，本项目没有手写 SQL。DTO 是前端提交进来的表单，VO 是返回给页面的展示对象，实体类对应数据库表。

包名统一是 com.office.purchase。接口返回都是 {"code":200,"msg":"...","data":...}。401 表示没登录，403 表示角色不对，500 表示业务没通过。

启动和公共类

启动类

PurchaseApplication

程序入口。Spring Boot 从这里启动内置 Tomcat，@MapperScan 扫描全部 Mapper。

  • main：调用 SpringApplication.run。

common

Result、PageResult

Result 是所有接口的外壳。PageResult 是分页外壳，页面表格使用 total、current、size、records。

  • Result.ok / fail：成功码 200，失败可以指定 401、403、500。
  • PageResult.of / empty：有数据的一页，或员工还没有订单时的空页。

common

BizException

可预期的业务错误，例如“仅待审批的申请可以审批”。抛出后由 GlobalExceptionHandler 转成前端能直接显示的句子，不把堆栈给页面。

common

RoleConst、StatusConst

把角色和状态集中成常量，避免各处手写字符串写错。

  • 角色：admin 管理员、audit 审核人员、staff 普通员工。valid 用来检查新用户的角色是否合法。
  • 申请状态：待审批、已通过、已驳回。
  • 订单状态：待采购、采购中、已到货、已完成。管理员只能改成这四种。

common

UserContext

用 ThreadLocal 保存当前请求的登录用户。拦截器放入，请求结束必须 clear，否则线程池复用时会串到下一个人。

annotation

RequireRole

标在控制器方法上，声明哪些角色可以调用。不标的接口只要登录就能访问，例如查看商品和公告。

配置和安全

config

WebMvcConfig

注册登录拦截器，并允许前端开发服务器跨域。登录接口 /user/login 被排除，其余接口都要经过 AuthInterceptor。

interceptor

AuthInterceptor

每个业务请求的门卫。静态页面和 SpaController 的转发直接放行。

  • preHandle：取出 Bearer 令牌，JwtUtil 解析，再按用户编号查数据库。用户被删了就拒绝。角色不在 RequireRole 里就返回 403。
  • afterCompletion：清理 UserContext。

配合：JwtUtil、UserMapper、RequireRole、UserContext。

util

JwtUtil

签发和解析登录令牌。令牌里只放用户编号和角色，真正的权限仍以数据库里的最新角色为准。

  • initSecret：读取环境变量 PURCHASE_JWT_SECRET。演示环境没配时，本次启动临时生成一把密钥，重启后要重新登录。
  • createToken / parse：登录成功时签发，拦截器里解析。

config

PasswordConfig

只提供 BCryptPasswordEncoder。没有启用整套 Spring Security 过滤器，登录校验是自己写的。

config

MybatisPlusConfig

注册分页插件。没有它时，Page 查询会把整张表查出来。H2 演示库开了 MySQL 模式，所以分页语法按 MySQL 的 LIMIT。

config

DemoDataInitializer

应用启动后，如果用户、商品或公告表是空的，就写入论文里的三个账号、八种办公用品和两条公告。已经有数据时不会覆盖，所以不会把别人改过的密码重置回去。

演示账号密码都是 123456，入库前会先 BCrypt 加密。

exception

GlobalExceptionHandler

把三类错误收成统一 JSON。

  • 参数校验失败：返回第一条中文提示，例如“请填写申请理由”。
  • BizException：返回业务原因。
  • 数据库唯一约束或外键冲突：提示可能重复或仍被引用。
  • 其他异常：只记日志，页面对用户显示“系统繁忙”。

controller

SpaController

前端打包进后端之后，用户刷新 /goods 这类地址时，浏览器要拿到 index.html，再由 Vue Router 显示对应页面。这个类只转发页面路径，不转发 /user、/goods/page 这类接口。

控制器

控制器对应前端能点到的动作。写操作看 RequireRole，查询类接口多数只要登录。

controller · /user

UserController

登录、当前用户、管理员维护账号、每个人改自己的密码。

  • POST /login：不需要令牌。
  • GET /me：刷新页面后确认自己是谁。
  • GET /page、POST、PUT、DELETE /{userId}、PUT /reset/{userId}：仅管理员。
  • PUT /password：当前用户修改自己的密码。

controller · /goods

GoodsController

商品查询对所有登录用户开放。新增、修改、删除只允许管理员。

  • GET /page：可按名称、类别筛选。提交申请页会一次取较多记录。
  • POST、PUT、DELETE /{goodsId}：维护商品档案。

controller · /apply

PurchaseApplyController

采购申请的入口。申请人编号从登录用户取，不信任前端传来的用户编号。

  • POST /submit：仅员工，提交新申请。
  • PUT /resubmit：仅员工，修改被驳回的申请。
  • GET /page、GET /{applyId}：查询。员工在 Service 里被限制成只能看自己的。
  • POST /audit：仅审核人员。

controller · /order

PurchaseOrderController

订单查询对登录用户开放，但员工只能看到自己的。改状态只允许管理员。

  • GET /page：可按状态和关键字筛选。
  • PUT /status：更新履约状态。

controller · /notice

NoticeController

公告所有登录用户都能看。发布、修改、删除只允许管理员。

  • GET /page、GET /latest：列表和首页最近几条。
  • POST、PUT、DELETE /{noticeId}：维护公告。

controller · /home

HomeController

工作台只提供一个接口 GET /summary。返回当前角色真正用得上的数量和最新公告，不返回别人的申请明细。

业务实现

接口 UserService、GoodsService、PurchaseApplyService、PurchaseOrderService、NoticeService、HomeService 只声明方法。真正的规则在下面这些实现类里。读业务时看 Impl，不用在接口和实现之间来回跳。

service.impl

UserServiceImpl

账号、密码和角色。密码只存 BCrypt 密文。

  • login：账号不存在和密码错误使用同一句提示，避免告诉别人账号是否存在。
  • createUser：检查角色和账号重复。
  • updateUser：不能取消自己的管理员身份，否则系统会没有管理员。
  • deleteUser：不能删除自己；已有申请或审批记录的用户不能删。
  • resetPassword：重置为 123456。
  • changePassword：必须先对上原密码，且新密码不能和原密码相同。

service.impl

GoodsServiceImpl

办公用品档案。单价保留两位小数。已被申请引用的商品不能删除，否则历史明细会失去名称。库存只在这里由管理员修改，审批通过不会扣减。

service.impl

PurchaseApplyServiceImpl

本系统最重要的类。提交、重提、查询和审批都在这里。

  • submit：校验商品存在、同一申请不能重复选择同一商品，然后保存主表和明细，状态为待审批。
  • resubmit：必须是申请人本人，且当前状态是已驳回。重提后清空上次审批人、意见和时间，换掉明细。
  • pageApplies / detail：员工只能看自己的申请。
  • audit：只处理待审批单据。驳回必须有意见。通过时如果还没有订单，就插入状态为待采购的订单。两步在同一个事务里，失败会一起回滚。

service.impl

PurchaseOrderServiceImpl

订单不是人手新建的，只在审批通过时生成。这个类负责查询和改状态。

  • pageOrders：员工先找出自己的申请编号，再查这些申请对应的订单。管理员和审核人员看全部。
  • updateStatus：只接受 StatusConst 里的四种状态。

service.impl

NoticeServiceImpl

公告的增删改查。修改公告时会把发布时间更新成现在，让改过的公告回到列表前面。latest 给工作台用，最多 20 条。

service.impl

HomeServiceImpl

按角色统计工作台数字。员工看到自己的待审批、已驳回和订单数。审核人员和管理员看到全库待审批数、订单数和商品数。统计口径和对应列表一致。

service.support

ApplyViewAssembler

列表如果逐条查商品和用户，会很慢。这个类按一批申请编号取出明细，补上商品名、规格和金额，并生成“签字笔×2、打印纸×1”这样的摘要。

明细表没有保存下单时的单价，所以金额按商品当前单价计算。商品已删除时，名称显示“商品已删除”，金额按 0。

实体类

实体类和数据库表一一对应，字段用下划线转驼峰。它们不写业务规则。

entity · 表 user

User

登录账号、加密密码、姓名、角色、手机号、创建时间。表名加了反引号，避免 H2 把 user 当成关键字。密码字段有 @JsonIgnore，接口不会把密文返回给前端。

entity · 表 goods

Goods

商品名称、类别、规格、单价、库存、录入时间。

entity · 表 purchase_apply

PurchaseApply

一张采购申请：谁申请的、理由、提交时间、审批状态、谁审的、审批意见和审批时间。

entity · 表 purchase_apply_item

PurchaseApplyItem

申请明细。一张申请可以有多行，每行是一个商品和采购数量。

entity · 表 purchase_order

PurchaseOrder

由申请生成的订单。一张申请最多一张订单，所以 apply_id 有唯一约束。

entity · 表 notice

Notice

公告标题、正文和发布时间。

Mapper

mapper

六张表各有一个 Mapper

UserMapper、GoodsMapper、PurchaseApplyMapper、PurchaseApplyItemMapper、PurchaseOrderMapper、NoticeMapper 都继承 MyBatis-Plus 的 BaseMapper。因此新增、按主键查询、按条件更新、删除和分页都不需要 XML。

GoodsMapper 上的注释写明了这一点，对应论文里的 Mapper 示例。复杂组装不写 SQL，交给 ApplyViewAssembler 在 Java 里完成。

DTO

DTO 是请求体。字段上的注解负责第一层校验，Service 里还有业务校验。

LoginDTO

登录只收账号和密码。

PasswordDTO

修改自己的密码：原密码、新密码。新密码 6 到 20 位。

UserCreateDTO

管理员新增用户。账号以字母开头，只能含字母、数字和下划线。同时指定初始密码、姓名、角色和可选手机号。

UserUpdateDTO

修改姓名、角色和手机号。账号创建后不能改，避免历史单据对不上人。

GoodsSaveDTO

新增或修改商品。修改时必须带 goodsId。单价不能为负，库存不能为负。

ApplySubmitDTO、ApplyItemDTO

提交和重新提交共用。理由必填，至少一种商品。重新提交时多带 applyId。每行明细是商品编号和数量，数量至少为 1。

AuditDTO

审批结论只能在 Service 里接受“已通过”或“已驳回”。驳回意见在 Service 里强制要求，不放在注解里，因为通过时可以不填。

OrderStatusDTO

管理员更新订单时提交订单编号和目标状态。

NoticeSaveDTO

公告标题和正文。修改时带 noticeId。

VO

VO 是返回给页面的对象，可以拼上表里没有的姓名和金额。

LoginVO

登录成功后的令牌、用户编号、账号、姓名、角色、手机号。没有密码。

ApplyItemVO

一条明细的商品名、规格、单价、数量和金额。

ApplyListVO

申请列表的一行。明细被收成 goodsSummary，避免表格太宽。

ApplyDetailVO

申请详情，给查看、审批和重新提交前回显。包含全部明细。

OrderVO

订单加上申请人、申请理由、明细摘要和金额。

HomeSummaryVO

工作台需要的姓名、角色、各类数量和最新公告列表。

test

PurchaseFlowTest

用 H2 把主流程跑一遍，不依赖本机 MySQL。它检查演示密码密文是否对应 123456，然后走：员工提交、审核驳回、员工重提、审核通过并生成订单、管理员把订单改为已到货。中途还确认员工不能新增商品，也不能改订单状态。

前端文件

前端不是 Java 类，但答辩时经常被问到页面和接口怎么对上。开发时页面在 8081，请求以 /api 开头，由 Vite 去掉前缀后转发到 8080。演示镜像里没有单独的前端服务，页面已经被打进后端。

main.js、App.vue

挂载 Vue，并安装 Element-UI 的中文语言包。App 只放一个路由出口。

router/index.js

定义每个页面的地址和允许的角色。没登录去登录页，角色不对回工作台。

utils/request.js

Axios 实例。自动带令牌；code 不是 200 时弹出 msg；401 时清除本地登录状态并回到登录页。

api/index.js

把每个后端接口包成一个函数，页面不直接写 URL。

utils/dict.js、components/Stamp.vue

角色中文名，以及用印章样式显示待审批、已通过、已驳回和订单状态。颜色只是辅助，文字仍然可读。

layout/Layout.vue

登录后的外壳。按 admin、audit、staff 显示不同菜单，并提供退出。

views/Login.vue

登录表单。成功后把令牌和用户信息放进 localStorage。

views/Home.vue

工作台。调用 /home/summary，按角色显示该处理的数量和公告。

views/goods/GoodsList.vue

商品台账。管理员看到新增、修改、删除，其他角色只读。

views/apply/ApplySubmit.vue

员工选品。数量为 0 的行不会提交。

views/apply/ApplyTable.vue

三处复用：我的申请、待我审批、全部申请记录。审批和重新提交都在这个组件里完成。

views/order/OrderList.vue

订单列表。只有管理员能打开“更新状态”。

views/user/UserList.vue

管理员维护用户、重置密码和删除用户。

views/notice/NoticeList.vue

公告栏。管理员在上方编写，所有人在下方阅读。

views/profile/Password.vue

修改当前账号密码。成功后清除登录状态，要求重新登录。

配置文件

application.yml 和 application-h2.yml

默认配置指向 MySQL，密码来自环境变量 DB_PASSWORD，不写死在仓库里。演示镜像设置 SPRING_PROFILES_ACTIVE=h2 后，改用内存数据库，并执行 db/schema-h2.sql 建表。H2 的表结构跟论文里的六张表一致，只是去掉了 MySQL 专有的引擎和注释语法。
