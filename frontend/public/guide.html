给第一次读代码的同学

你不用先把所有文件看懂

这份说明书假设你是大一新生，还没学过 Spring Boot，也分不清什么是接口。你只要会用浏览器，就能先把这个系统看明白。

代码很多，是因为它把一件小事拆开了：有人负责接待，有人负责做决定，有人负责往本子上记账。你先记住这件事，再去认每一块代码的名字。

这个系统是干什么的

办公室里的打印纸、笔、文件夹用完了，以前要填一张纸质申请单，拿去找人签字，签完再让行政去买。

这个系统把这件事搬到网页上。员工在网页里选东西、写理由。审核的人在网页里点“通过”或“驳回”。通过之后，系统自动记下一张订单。管理员再把订单改成“采购中”“已到货”或“已完成”。

演示账号的密码都是 123456。员工 staff01，审核 audit01，管理员 admin。你可以自己登进去点一遍，再回来对故事。

先认识六个词

类。一个有名字的代码文件，里面放一组相关的动作。文件名 UserController.java 里的类就叫 UserController。你可以把类想成一个岗位。

前端。你在浏览器里看见的页面、按钮、表格。这个项目的前端用 Vue 写，文件大多是 .vue。

后端。页面背后那个做判断的程序。它决定密码对不对、这个人能不能审批。后端用 Java 写，跑在 Spring Boot 里。

数据库。用来记住事情的表格本子。商品、申请、订单都记在不同的表里。演示环境用的是 H2，数据放在内存里，程序一关，新填的内容就没了。

接口。页面找后端办事的地址。比如登录的地址是 /user/login。页面把账号密码送过去，后端回一句“登录成功”和一张通行证。

表。数据库里的一张格子表。一行是一件事，比如一种商品，或一张申请单。

跟着小王走一遍

小王是普通员工。办公室的 A4 纸不够了。下面每一步只告诉你：谁在说话，说到了哪一个类。

1. 打开网页，输入账号密码

你看见的登录页是 Login.vue。它只负责把你输入的字收下来，自己并不检查密码对不对。

它把账号和密码送到后端的 UserController。这个类是“用户这件事的前台”。前台不自己做决定，把活交给 UserServiceImpl。

UserServiceImpl 去用户表里找这个账号。数据库里的密码不是明文 123456，而是打乱后的一长串。PasswordConfig 提供比对工具。对上了，JwtUtil 发一张临时通行证。页面把它记在浏览器里。

2. 之后每点一个按钮，都要出示通行证

request.js 负责在每次请求上贴上这张通行证。AuthInterceptor 是门口保安：没有通行证，或者通行证过期，就请你重新登录。保安还会看方法上的标记 RequireRole。那是一张“只允许管理员”或“只允许审核员”的牌子。员工硬闯管理员的功能，会被拦住。

保安确认身份后，把这个人暂时放到 UserContext 里。后面的代码就能知道“现在操作的是小王”，不用再问一遍。

3. 看有哪些商品

商品页面是 GoodsList.vue。它找 GoodsController，再找 GoodsServiceImpl，最后由 GoodsMapper 去商品表把名称、单价、库存读出来。

Mapper 可以理解成“专门翻某一张表的人”。他不会决定能不能买，只会按要求读和写。

4. 选好数量，写下理由，提交申请

提交页面是 ApplySubmit.vue。数量填 0 的商品不会被送出去。

请求到了 PurchaseApplyController。它先确认你是员工，再把你的用户编号交给 PurchaseApplyServiceImpl。这个类是整件事的核心：

它检查商品还在不在、同一张单里有没有把同一种东西选了两次。然后在申请表写一行，状态写成“待审批”，再在明细表写下每种东西要多少。这两下必须一起成功。如果写到一半失败，两下都取消，避免出现“有申请单但没有买什么”的空单。

5. 审核员登录，点通过或驳回

审核员看到的列表来自 ApplyTable.vue。点通过或驳回，还是进 PurchaseApplyController，但这次牌子上写着“只有审核员”。

驳回时必须写原因，否则小王不知道改什么。通过时，PurchaseApplyServiceImpl 把申请改成“已通过”，并立刻新建一张订单，状态是“待采购”。订单不是人手新建的，是审批通过时自动出现的。

如果小王的申请被驳回，他可以在“我的申请”里修改数量和理由，再提交。这叫重提。重提后，上次的驳回意见会被清掉，状态回到“待审批”。

6. 管理员更新到货进度

订单页面是 OrderList.vue。小王只能看见自己的订单。管理员能看见全部，并且能把状态改成采购中、已到货或已完成。真正改状态的是 PurchaseOrderServiceImpl。

注意：申请通过以后，商品库存的数字不会自动减少。库存要管理员到商品页面里自己改。这不是漏做，论文里把“自动扣库存”留成了以后再做的功能。

页面上的字是怎么拼出来的

数据库里的申请只记了“用户编号 3、商品编号 1、数量 2”。页面却要显示“普通员工买了 A4 打印纸 2 包，一共多少钱”。ApplyViewAssembler 就是做这件事的人：按编号把姓名、商品名和金额补上，再收成一句“A4打印纸×2”。

词典：公共小工具

这些类没有业务故事，但别的类天天用它们。知道它们是“公用文具”就够了。

PurchaseApplication 启动开关

双击运行后端时，真正被先叫起来的就是这个类。它把整个程序打开，并告诉程序去哪里找那些 Mapper。

Result 统一的回信格式

后端给页面的每封回信都长一样：成功还是失败、一句话说明、真正的数据。成功时 code 是 200。没登录是 401，没有权限是 403，事情没做成是 500。这样页面不用为每个功能单独猜回信长什么样。

PageResult 翻页用的盒子

商品、申请、订单可能有很多行。这个盒子告诉页面：一共多少条、现在第几页、这一页有哪些行。没有数据时用空盒子，页面就显示“还没有订单”。

BizException 可以告诉用户的错误

比如“只有被驳回的申请才能修改”。这不是程序崩溃，而是规则不允许。抛出它之后，页面上会直接看到这句话。

RoleConst 三种人的代号

管理员 admin，审核员 audit，员工 staff。集中写在这里，避免有的地方写成“管理员”，有的地方写成 admin，对不上。

StatusConst 状态的标准写法

申请只有三种：待审批、已通过、已驳回。订单只有四种：待采购、采购中、已到货、已完成。改状态时只允许这几个字。

UserContext 当前是谁

一次请求处理期间，把登录的人放在手里。请求结束必须丢掉，不然下一次可能误当成同一个人。

RequireRole 门上的牌子

贴在某个功能上，写明哪些角色能进。没贴牌子的功能，只要登录了就能用，比如看商品、看公告。

GlobalExceptionHandler 错误翻译员

程序里出现的错误，有的是你没填理由，有的是规则不允许，有的是真的坏了。这个类把它们都变成页面能显示的一句中文。真正的故障细节只写进日志，不甩给用户。

词典：程序启动时做的准备

WebMvcConfig

安排保安站在哪里。除了登录，其它接口都要先经过 AuthInterceptor。开发时页面在 8081、程序在 8080，它也负责允许这种跨地址访问。

AuthInterceptor 保安

检查通行证，查出这个人现在的角色，再看门上的牌子。角色以数据库里最新的为准，不轻信通行证上旧的字。页面文件本身不用检查，不然你连登录页都打不开。

JwtUtil 通行证制作处

登录成功就做一张有期限的通行证。上面有用户编号。没人配置密钥时，这次启动会临时做一把锁。程序重启后，旧通行证就失效了，需要重新登录。

PasswordConfig

准备密码比对工具。数据库不保存你输入的那串原文。比对时是拿你刚输入的密码，去对那串打乱后的结果。

MybatisPlusConfig

让列表真的按页取数据。没有这个配置，所谓的“第一页”可能会把整张表都取出来。

DemoDataInitializer 第一次开机的样例数据

如果用户、商品、公告还是空的，就放进三个演示账号、几种文具和两条公告。已经有数据时不会覆盖，所以不会把别人改过的密码又变回 123456。

SpaController

演示镜像里，网页和后端是一起启动的。你在浏览器刷新“商品”这一页时，服务器先把网页壳子交回来，再由网页自己决定显示商品。这个类就是交回那个壳子。它不处理真正的业务。

词典：所有入口

入口类的名字都以 Controller 结尾。它们像前台：接收页面送来的内容，检查是谁，然后把活交给业务类。前台自己不算账。

UserController /user

登录、查看“我是谁”、管理员新增和删除用户、重置别人的密码、每个人改自己的密码。登录这一下不需要通行证，其它都要。

GoodsController /goods

谁都能看商品。只有管理员能新增、修改、删除。

PurchaseApplyController /apply

员工提交申请、驳回后重提、所有人按权限查看、审核员审批。申请人是谁，以前台认出的登录用户为准，不采用页面自己填的用户编号，防止冒充别人申请。

PurchaseOrderController /order

查看订单。改状态的入口只给管理员。

NoticeController /notice

谁都能看公告。只有管理员能发布、修改、删除。

HomeController /home

登录后的第一屏。只回答“你现在有几件要处理的事”和“最新公告”。员工不会在这里看见别人的申请内容。

词典：真正做决定的类

你会看到两份很像的名字，比如 UserService 和 UserServiceImpl。Service 像菜单，只写有哪些功能。Impl 是后厨，规则写在这里。第一次读，看 Impl 就够了。

UserService

菜单。列出登录、建用户、改资料、删除、重置密码、改自己的密码。没有具体步骤。

UserServiceImpl

账号和密码的规则都在这里。账号不存在和密码错误，提示同一句话，避免别人试出哪些账号是真的。不能删除自己。已经写过申请或审过单的人不能删，否则旧单据会找不到人。管理员不能把自己的管理员身份取消掉。

GoodsService

商品功能的菜单：查询、新增、修改、删除。

GoodsServiceImpl

保存商品时把单价整理成两位小数。已经被人申请过的商品不能删除，不然旧申请会变成“不知道买的是什么”。

PurchaseApplyService

申请功能的菜单：提交、重提、查询、看详情、审批。

PurchaseOrderService

订单功能的菜单：查询、改状态。没有“新建订单”，因为订单只在审批通过时出现。

NoticeService

公告功能的菜单。

NoticeServiceImpl

发布和修改公告。修改后把发布时间改成现在，这样刚改过的公告会排到前面。首页只要最近几条。

HomeService

工作台功能的菜单，只有一个方法：按当前这个人统计数字。

HomeServiceImpl

员工看自己的待审批、被驳回和订单数。审核员和管理员看全部待审批、全部订单和商品种类数。数字和对应列表是同一套算法，不会出现首页写 3 条、点进去却是 5 条。

ApplyViewAssembler 把编号翻译成人话

列表如果每一行都单独查一次姓名和商品，会很慢。这个类一次把一批申请的明细补齐，算出金额，并生成简短摘要。金额用的是商品现在的单价，因为明细表里没有记住下单那一刻的价格。

词典：表、交上来的表格、返回去的表格

同一件事会有三种样子，不要吓到。实体是数据库里的一行。DTO 是页面交上来的表单，上面有“必填”之类的检查。VO 是整理好再还给页面的内容，可以多出数据库里没有的姓名和金额。

User 用户表

账号、打乱后的密码、姓名、角色、手机号、创建时间。密码不会跟着接口回到页面上。

Goods 商品表

名称、类别、规格、单价、库存、录入时间。

PurchaseApply 申请表

谁申请的、为什么申请、什么时候交的、现在是待审批还是已通过或已驳回、谁审的、审了什么意见。

PurchaseApplyItem 申请明细表

一张申请可以买好几种东西。每种东西一行：哪个商品、要多少。

PurchaseOrder 订单表

对应哪张申请、订单状态、什么时候生成的。一张申请最多一张订单。

Notice 公告表

标题、正文、发布时间。

六个 Mapper

UserMapper、GoodsMapper、PurchaseApplyMapper、PurchaseApplyItemMapper、PurchaseOrderMapper、NoticeMapper。一个 Mapper 对应上面一张表。它们继承现成工具，所以普通的新增、查询、修改、删除不用再写 SQL。你可以把它理解成：每张表配了一个保管员，保管员不制定规则。

LoginDTO

登录时交上来的两格：账号、密码。不能空着。

PasswordDTO

改自己的密码：旧密码、新密码。新密码要 6 到 20 位。

UserCreateDTO

管理员新建用户时交的表：账号、初始密码、姓名、角色、手机号。账号要用字母开头。

UserUpdateDTO

修改用户时不能改账号，只能改姓名、角色和手机号。账号一改，旧单据就对不上人了。

GoodsSaveDTO

新增或修改商品。修改时要带上商品编号。单价和库存不能是负数。

ApplySubmitDTO 和 ApplyItemDTO

提交申请时的理由，加上至少一种商品。每种商品是编号和数量。重新提交时还要带上原来的申请编号。

AuditDTO

审核员交上来的结论：通过还是驳回，以及意见。驳回却不写意见，会在业务类里被拒绝。

OrderStatusDTO

管理员改订单时交的两格：哪张订单、改成哪个状态。

NoticeSaveDTO

公告的标题和正文。修改时带上公告编号。

LoginVO

登录成功后交回页面的内容：通行证、你的编号、账号、姓名、角色、手机号。没有密码。

ApplyItemVO

页面上的一行明细：商品名、规格、单价、数量、金额。

ApplyListVO

申请列表的一行。东西太多时不把每件都铺开，而是收成一句摘要。

ApplyDetailVO

点开一张申请后看到的全部内容，包括每件商品。审批和重新提交前都靠它回显。

OrderVO

订单列表上的一行，补上了申请人、理由、买了什么和金额。

HomeSummaryVO

工作台要的那几个数字，外加最新公告。

PurchaseFlowTest 自动检查主流程

这不是给用户点的页面。它是一段自动测验：假装员工提交、审核员驳回、员工修改后再交、审核员通过、管理员把订单改成已到货，并确认员工不能去做管理员的事。老师或你自己运行测试时，它用来证明主流程没断。

页面文件，用生活语言再说一次

main.js 和 App.vue

把网页程序启动起来，并装上现成的按钮、表格样式。App 本身几乎是空的，只是一个用来切换页面的框。

router/index.js

网址和页面的对照表。没登录就只能停在登录页。员工如果手动输入管理员的网址，会被送回工作台。

utils/request.js 和 api/index.js

request 是所有请求的公用邮差，负责贴通行证、弹出失败原因。api 把每个地址包成一个好记的函数，页面就不用反复写那串地址。

Layout.vue

登录之后左边的菜单。三种人看见的菜单不一样。

Home.vue

工作台。告诉你下一步该干什么，并列出公告。

GoodsList.vue

商品表格。管理员多出新增、修改、删除。

ApplySubmit.vue

员工选东西、写理由、提交。

ApplyTable.vue

一张表三处用：我的申请、待我审批、全部申请。审批按钮和“重新提交”也在这里。

OrderList.vue

订单表。只有管理员看得到“更新状态”。

UserList.vue

你现在可以怎么读代码

第一次只打开这 4 个文件，顺着小王的故事看：

1. Login.vue，看页面把什么送出去。
2. UserController.java，看前台把活交给谁。
3. PurchaseApplyServiceImpl.java，看申请如何变成“待审批”，通过后又如何生出订单。
4. AuthInterceptor.java，看没有登录的人为什么进不去。

看懂这一圈之后，其它类都是同一套办法：页面收集内容，Controller 接待，ServiceImpl 做决定，Mapper 去表里读写。
